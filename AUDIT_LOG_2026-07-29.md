## 2. Bugs fixed

**`core/mt5_history_sync.py` — open_price/close_price duplication.**
Every closed-trade row had `open_price == close_price` because the sync
loop (which only ever sees the *closing* deal) wrote `deal.price` into both
columns. Fixed by indexing opening deals (`entry == 0`) by `position_id`
before the loop and looking up the real entry price per closing deal, with
a fallback to the old behavior only if no opening deal is in the fetched
window. Also fixes `entry_price` on the `truth_layer` `TradeRecord`, which
was previously hardcoded to `0.0`.

**Certification blending retired-version trades with current-build trades.**
`certification/framework.py::_closed_rows()` now filters to
`build_id == BUILD_ID` (see #3). `certification_status.md` was regenerated
after the fix and backfill below — it now reports the real number:
**20 closed trades, 40% WR, -$161.23, 20/100 toward certification.**

## 3. Build/version tagging (prevents recurrence)

Added `BUILD_ID = 'FER3ON-FINAL-build1'` (`core/settings.py`) and a
`build_id` column/field stamped at every write site:
- `core/trade_logger.py::log_trade()` (open-time row, called via
  `trade_executor.py`'s `persist_trade_log` alias)
- `core/mt5_history_sync.py` (close-time sync, both the `trades.csv`
  fallback-insert path and the `mt5_trade_history.csv` writer)
- `analytics/truth_layer.py::TradeRecord` (new top-level field)

**Defensive guard added:** `log_trade()` now raises `ValueError` if `ticket`
or `strategy` is missing, rather than silently writing an untraceable row.
This is the single write path for every `trades.csv` row, so it makes the
57-row pollution pattern structurally impossible going forward, regardless
of what originally caused it.

### 7. `QUANT_HEALTH` / `risk_multiplier` was blending builds too

`📊 QUANT_HEALTH | SMC | tier=POOR | n=82 | ... → risk_multiplier=0.30`
followed by `QUANT_LOT_ADJUST | SMC | tier=POOR | lot 0.08 → 0.02 (×0.3)`.

`n=82` is far more than this build's real SMC trade count. Traced it to
`analytics/quant_engine.py::evaluate_strategy_health()`, which calls
`filter_trades(load_all_trades(), strategy=strat)` with **no build_id
filter** — unlike `certification/framework.py`, this consumer wasn't
touched by the first pass. Per its own header comment, this function's
`risk_multiplier` output is consumed directly by:
- `core/trade_executor.py` — real position-size scaling (`QUANT_LOT_ADJUST`)
- `core/unified_decision.py` — `QUANT_HEALTH_STRONG`/`QUANT_HEALTH_WEAK`
  scoring bonus/penalty on every entry decision

So this wasn't just a wrong number in a report — it was a real trading
decision (lot cut to 30%, entry scoring penalized) being driven by a sample
blended from a retired strategy version.

**Fix:** `analytics/truth_layer.py::filter_trades()` now accepts a
`build_id` argument; `evaluate_strategy_health()` passes `BUILD_ID` through
it. Verified against the backfilled real data: `SMC` now reports
`sample_size=17` (this build's actual real SMC trade count) instead of 82,
tier `UNKNOWN` (below `QUANT_MIN_TRADES_FOR_HEALTH=20`), `risk_multiplier=1.0`
(neutral) instead of the previous artificially-suppressed 0.30. New
regression test: `tests/test_quant_engine_build_id_fix.py`.

**Practical effect once جو re-syncs on the real machine:** SMC/MICRO lot
sizing will no longer be cut by the old build's poor track record. It'll run
at neutral (1.0×) sizing until each strategy separately accumulates 20+ real
trades under `build_id=FER3ON-FINAL-build1`, then start scoring on its own
actual merits.

### 9. `truth_layer` records were being silently duplicated — root cause found

While reviewing the full file, `sync_csv_to_truth_layer()` (the
"CSV_BRIDGE" step, called once at startup) kept "syncing" trades that
`sync_mt5_history()` had, in the same run, already written moments earlier
— both burn-in logs showed this (`synced=2` every single run, never
trending toward 0 as expected once a trade's really been synced once).

Traced to a genuine, **pre-existing** bug (not introduced by this audit):
`core/mt5_history_sync.py` wrote the `truth_layer` `TradeRecord` with
`ticket=int(deal.ticket)` — the closing **deal's own id** — while
`trades.csv` (and everything else: `ai_memory`, `portfolio_risk_authority`)
keys the same trade by `close_ticket` (`position_id`, i.e. the **position**
ticket). `sync_csv_to_truth_layer()` dedupes by comparing `trades.csv`'s
ticket column against `truth_layer`'s existing ticket set — since the two
files used different numbering schemes, they could never match.

**Confirmed empirically** against the real backfilled data: zero overlap
between the 20 `truth_layer` ticket values and the 20 `trades.csv` ticket
values for what should be the exact same 20 trades.

**Effect:** every real trade was silently duplicated into `truth_layer` —
once correctly tagged (`build_id=FER3ON-FINAL-build1`, wrong ticket, from
`mt5_history_sync`) and once with `build_id=""` (blank, since
`csv_truth_bridge.py`'s CSV→TradeRecord conversion also didn't carry
`build_id` through — separately fixed, see below) under the correct
ticket. The `build_id` filter added earlier (#3, #7) meant this didn't
inflate `evaluate_strategy_health()`'s sample size — the blank-tagged
duplicates were already excluded — but it **would** inflate total
trade/profit counts for any future consumer of `load_all_trades()` that
doesn't filter by build_id (dashboards, ad-hoc scripts, etc.), and it's
exactly why the CSV bridge kept reporting `synced=2` every run instead of
trending to 0.

**Fixes:**
- `core/mt5_history_sync.py`: `TradeRecord.ticket` now uses `close_ticket`
  (matches `trades.csv`'s key), not `deal.ticket`. The original deal id is
  kept in `extra.deal_ticket` for audit purposes, nothing lost.
- `analytics/csv_truth_bridge.py::_csv_row_to_trade_record()`: now carries
  `build_id` through from the CSV row instead of dropping it — defense in
  depth for any trade that reaches `truth_layer` only via this bridge.
- New regression test:
  `tests/test_mt5_history_sync_merge_fix.py::test_truth_layer_record_keyed_by_position_ticket_not_deal_ticket`.

**Cleanup tool for the duplicates already sitting in a live file:**
`tools/dedupe_truth_layer.py` (dry-run by default, `--apply` to write).
Matches a bridge-created row (`build_id=""`, `extra.source=csv_truth_bridge`)
against a properly-tagged row (`build_id` set, `extra.source=mt5_history_sync`)
sharing the same `(strategy, profit, lot, close_date)`, and removes only
the bridge-created half of each matched pair — originals and anything it
can't confidently match are left untouched. Removed rows are preserved in
`data/truth_layer/trade_history_dedupe_removed.jsonl` for audit, and a
`.dedupe.bak` of the original file is kept. Verified against a synthetic
fixture reproducing the exact real-data pattern before trusting it.

## Addendum 3 (same day) — the code fix alone wasn't enough; shipped data needed correcting too

جو ran a genuinely fresh extraction (a new folder, `... (2)`) — so this
wasn't drift, it was the Addendum 2 fix being exercised for real for the
first time. The burn-in log showed:

```
✅ CSV_BRIDGE | synced=20 | skipped_open=14 | already_exists=0
📊 QUANT_HEALTH | SMC | tier=POOR | n=34 | ... → risk_multiplier=0.30
📊 QUANT_LOT_ADJUST | SMC | tier=POOR | lot 0.06 → 0.02 (×0.3)
```

`n=34` = exactly `17 × 2`. The Addendum 2 code fix (correct `ticket` going
forward, `build_id` propagated through the bridge) was working exactly as
designed — but it only affects *newly written* records. The 20 real trades
already sitting in the **shipped** `data/truth_layer/trade_history.json`
still had their old, wrong `ticket` value (`deal.ticket`, baked in before
the fix existed) — `tools/backfill_build_id.py` only ever added the
`build_id` field, it never touched `ticket`. So on a fresh run:
`sync_csv_to_truth_layer()` still couldn't match those 20 old records
against `trades.csv`'s tickets, created 20 fresh duplicates — and because
the *other* half of the Addendum 2 fix now correctly stamps `build_id` on
bridge-created rows, those 20 fresh duplicates counted too. Net effect:
fixing the bug made a specific consequence of it *worse* until the
already-shipped data was corrected to match — the honest n=17 became a
falsely-more-confident-looking n=34, same `POOR/0.30` verdict, still
silently cutting this trade's real lot size (0.06 → 0.02).

**Fix:** `tools/fix_truth_layer_ticket_keys.py` — one-time migration,
scoped strictly to `build_id == BUILD_ID` records only (see below), that
corrects the `ticket` field on the 20 already-shipped records to match
`trades.csv`'s `close_ticket`, matching by `(strategy, profit, close_date)`
with lot as a tie-breaker only (lot can differ slightly between a
position's requested size and its actual filled `deal.volume`, which was
initially causing false negatives — 15/20 matched before this was
relaxed) and a same-day-boundary fallback for one record where
`trades.csv`'s "date" (written when a sync cycle upserted the row) and
`truth_layer`'s `close_time` (the deal's actual timestamp) landed on
different UTC calendar dates a few hours apart.

**A real near-miss caught before applying:** the first version of this
migration (before adding the `build_id == BUILD_ID` guard) matched a
**legacy** July-17 trade (ticket `9288904426`, profit exactly `-10.0`) to
a current-build `trades.csv` row purely because they happened to share the
same profit value and strategy. Caught by inspecting the dry-run output
line by line before running `--apply`, not by the script itself — added
the explicit build_id guard afterward so this class of mismatch can't
happen structurally, not just because this particular coincidence was
noticed.

**Applied and verified** against the shipped data in this delivery:
- Ticket overlap between `truth_layer` and `trades.csv`: 0/20 → **20/20**.
- Re-ran `sync_csv_to_truth_layer()` against the corrected data:
  `synced=0 | already_exists=20` (was `synced=20 | already_exists=0`).
  `trade_history.json` stayed at 79 lines — no new duplicates created.
- `evaluate_strategy_health('SMC')`: `sample_size=17` (honest, was 34),
  `risk_multiplier=1.0` (neutral, correctly below the 20-trade minimum).
